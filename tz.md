# Техническое задание: личный планировщик расходов

Версия: 1.1. Дата изменения способа запуска: 15 октября 2026 года. Язык интерфейса: русский.

## Согласованное изменение: PWA на Android

15 октября 2026 года после неуспешного локального запуска на TECNO Camon 30 / Android 16 / Chrome пользователь выбрал второй предложенный вариант — устанавливаемое веб-приложение (PWA). Это разрешение реализовать и разместить статические файлы по HTTPS. Требования этого раздела имеют приоритет над прежними ограничениями о трёх файлах и обязательном запуске через file:// ниже; финансовые требования не меняются.

- Основной запуск — по постоянной HTTPS-ссылке в Chrome, затем со значка на главном экране в режиме standalone. Первоначальная загрузка и получение новых версий требуют интернета; после полной подготовки приложение должно открываться без сети, включая новую вкладку и повторный запуск.
- К index.html, style.css и script.js добавляются pwa.js, manifest.webmanifest, sw.js и PNG-значки. Внешние библиотеки и сборка не требуются. Служебный каталог публикации и конфигурация хостинга не содержат финансовых записей.
- Manifest использует относительные id/start_url/scope, русский язык, имя приложения, standalone, обычные значки 192/512 px и отдельный maskable 512 px. Все файлы одного выпуска сохраняются локальным service worker до объявления готовности к offline.
- В мастере и настройках есть состояние подготовки/offline, инструкция установки через Chrome, кнопка установки при доступном системном событии и проверка обновлений. Отмена или отсутствие системного предложения не мешает работе самого журнала.
- Новый service worker не заменяет работающую версию принудительно. Обновление ждёт закрытия всех окон прежней версии; сообщение предлагает сначала сохранить поля. Никаких автоматических перезагрузок открытой формы.
- Worker обслуживает только собственные статические файлы и стартовую страницу в своей области; не перехватывает сторонние сайты, POST или авторизацию хостинга. Новая версия удаляет только старые кеши приложения; localStorage и JSON-копии не очищаются.
- Все доходы, расходы, настройки, точки и копии остаются в браузере, без базы данных и отправки финансовых данных на хостинг. Схема, ключи и правила финансового хранения сохраняются. Другой домен/браузер/локальный файл — другая область хранения: перенос через экспорт/импорт JSON. Очистка данных сайта может удалить журнал; копии по-прежнему нужны.
- HTTPS-размещение — статический хостинг Sites, изначально с частным доступом владельца. Для первого онлайн-входа может потребоваться авторизация владельца на хостинге; финансового аккаунта внутри планировщика нет. Расширять аудиторию без отдельного запроса нельзя.
- **AT-36 в новой редакции:** на реальном Android открыть опубликованный HTTPS-адрес, дождаться offline-готовности, установить значок, создать запись и выбрать тему; закрыть приложение/Chrome и открыть со значка без сети; проверить данные, CSS/JS, экранную клавиатуру, импорт/экспорт JSON. Физический телефон проверяет пользователь; настольная эмуляция этого не заменяет.
- **AT-37:** на компьютере проверить manifest, значки и область worker, полный кеш, холодное offline-открытие и повторное сохранение/импорт/экспорт, отказ первой подготовки, неудачное обновление, ожидание новой версии при открытой изменённой форме, применение после закрытия всех клиентов и сохранность финансового JSON/темы. Финансовые проверки AT-01–AT-35 остаются обязательными.

Документ описывает первую версию продукта и является основным источником требований для разработчика, в том числе нейросети. При расхождении с `concept.md` использовать это ТЗ: оно учитывает последние ответы пользователя. Вопросов, отложенных на этап программирования, нет. Технические решения, которые пользователь поручил выбрать самостоятельно, зафиксированы ниже.

На текущем этапе создаётся только ТЗ. Это не разрешение начинать разработку или создавать файлы страницы.

## 1. Цель и границы продукта

Продукт — личная веб-страница, которая сопоставляет доходы и сроки расходов, предлагает очередность оплат и показывает, хватает ли денег до каждого следующего поступления. Пользователь видит, что оплатить из зарплаты, что из аванса, сколько оставить на жизнь и какой резерв доступен из оставшихся денег.

Итоги по месяцам и выбранному календарному году помогают анализировать фактически полученные доходы и оплаченные расходы. Положительная разница доходов и расходов за месяц не заменяет проверку кассового разрыва внутри месяца.

### 1.1. Обязательная поставка

Ровно три файла приложения в одной папке:

| Файл | Назначение |
| --- | --- |
| `index.html` | Структура, экраны, формы, доступная разметка, сообщения начальной загрузки. |
| `style.css` | Адаптивная компоновка, две темы, состояния и печатные размеры элементов. |
| `script.js` | Вся логика, работа с данными, расчёты, отчёты, импорт/экспорт, обработчики интерфейса. |

Без сборки, установки зависимостей и обязательных библиотек. Классический внешний скрипт с `defer`, относительные ссылки на CSS и JS. Не использовать ES-модули, `fetch` для чтения локальных ресурсов, CDN, внешние шрифты или изображения. Допустимы системные шрифты, CSS-графика и встроенные SVG. Документы `concept.md` и `tz.md` не являются файлами приложения.

### 1.2. Зафиксированные решения

| Область | Решение |
| --- | --- |
| Пользователи | Один владелец данных, без аккаунтов, ролей доступа и регистрации. |
| Деньги | Рубли и копейки; один общий баланс всех средств. |
| Планирование | Текущий календарный месяц и служебный расчёт до следующего регулярного дохода после конца месяца. |
| Зарплата | По умолчанию 10-го числа; сумма задаётся пользователем. |
| Аванс | По умолчанию 25-го числа; сумма задаётся отдельно. |
| Выходные | Суббота/воскресенье переносятся на предшествующую пятницу. Праздники — ручная корректировка. |
| День дохода и платежа | Доход можно использовать для платежа с крайним сроком в тот же день. |
| Жизнь | Бюджет на период между регулярными поступлениями, фактические траты допускается записывать общей суммой. |
| Резерв | Желаемый резерв формируется из свободных денег после обязательств и бюджета на жизнь. |
| Оплата | Только целиком; быстрая галочка, сумма и дата затем могут быть исправлены. |
| Необязательная регулярная статья | Правило на выбор: переносить неоплаченный экземпляр или пропускать его. |
| Пропущенные месяцы | Создавать новые регулярные экземпляры только за текущий месяц. Уже созданные неоплаченные обязательства сохранять. |
| Аналитика | Текущий план и факт; для прошлых месяцев и года — фактические операции и категории. Первоначальные планы не архивировать. |
| Резервная копия | Экспорт/импорт одного JSON. CSV и Excel-экспорт не входят в первую версию. |
| Темы | Светлая «Бумага и баклажан» по умолчанию; тёмная «Чернильный атлас». |
| Устройство и запуск | Основное устройство — Android, запуск локально из файлов. Компьютер поддерживается дополнительно. |
| Хранение | Только localStorage; без базы данных, серверов, синхронизации и передачи финансовых данных наружу. |

### 1.3. Вне первой версии

Банковские интеграции, выполнение переводов, распознавание чеков, проценты и графики погашения кредитов, несколько кошельков, совместный семейный доступ, валюты кроме рубля, частичные оплаты, полный производственный календарь, пуш-уведомления, фоновые задачи при закрытой странице, PWA, размещение в интернете и прогнозы на год вперёд.

## 2. Пользователь и автоматические действия

Единственный пользователь — владелец планировщика. Он может создавать, редактировать, отменять и отмечать операции, настраивать доходы и расходы, корректировать остаток, просматривать отчёты, менять тему и управлять резервными копиями.

Приложение автоматически вычисляет рекомендации, переносит допустимые неоплаченные расходы, создаёт экземпляры текущего месяца, проверяет сроки и хранит изменения. Оно не выполняет реальные оплаты и не считает ожидаемый доход фактически полученным без отметки пользователя.

Не использовать термин «администратор»: отдельного административного интерфейса нет. Любой человек, открывший этот браузер на устройстве, технически имеет доступ к сохранённым данным; PIN и шифрование в первой версии не реализуются.

## 3. Термины и финансовые инварианты

| Термин | Определение |
| --- | --- |
| Шаблон | Правило ежемесячного дохода или расхода; само по себе не является фактической операцией. |
| Экземпляр | Конкретный доход или расход за конкретный исходный месяц. |
| Фактическая операция | Подтверждённое получение дохода или выполненная полная оплата. |
| Срок | Последняя допустимая календарная дата оплаты включительно. Срок расхода из-за выходных автоматически не меняется. |
| Рекомендованная дата | Рассчитанный день, когда предлагается оплатить расход. Может быть заменён ручной датой. |
| Период | Интервал от одного регулярного поступления до следующего, последний день не включает дату следующего дохода. |
| Бюджет на жизнь | Плановая сумма для продуктов и личных нужд на период; не фиктивная фактическая трата. |
| Резерв | Вычисленная защищаемая часть общего остатка; не отдельный банковский счёт и не расход. |
| Кассовый разрыв | В расчётный день денег не хватает на обязательные платежи даже без желаемого резерва. |
| Недостаток бюджета на жизнь | На платежи может хватать, но средств недостаточно для установленного бюджета на жизнь. |
| Точка остатка | Введённая пользователем сумма на конкретную дату с перечнем операций, уже учтённых в этой сумме. |

Обязательные инварианты:

1. Денежные значения хранятся целыми копейками; расчёты не используют дробные рубли.
2. Одному экземпляру соответствует не более одной активной фактической операции. Повторное нажатие не создаёт вторую оплату.
3. Получение дохода или оплата заменяет ожидаемую операцию фактической, а не прибавляется к ней второй раз.
4. Начальный остаток, его корректировки, резерв и неиспользованный бюджет не считаются фактическими доходами/расходами.
5. Фактическая операция относится к месяцу и году её фактической даты, независимо от исходного месяца обязательства.
6. Перенос или генерация шаблона не создаёт фактической операции.
7. Ручная корректировка остатка не очищает историю.
8. Нехватка денег не отменяет и не переносит обязательный платёж автоматически.
9. Изменение категории, названия или суммы шаблона не изменяет уже записанные фактические суммы.
10. Фактические расходы можно вводить даже при отрицательном остатке; приложение показывает проблему, но не запрещает записывать реальность.

## 4. Экраны и навигация

Четыре основных раздела: «План», «Итоги», «Регулярные», «Настройки». На телефоне — нижняя навигация из четырёх подписанных кнопок. Заголовок продукта — «Мой план расходов».

### 4.1. Первый запуск

Показывать мастер настройки, если `onboardingCompleted = false`:

1. Остаток на сегодня: значение обязательное, допустим ноль или отрицательное значение. Объяснение: сумма всех доступных денег, а не месячный доход.
2. Зарплата и аванс: дни 10 и 25 уже выбраны. Пользователь вводит положительные суммы или явно отключает соответствующее поступление. Вымышленных сумм нет.
3. Деньги на жизнь: две суммы по умолчанию для периодов после зарплаты и после аванса; отдельная сумма, сколько ещё нужно на оставшуюся часть текущего периода. Ноль допустим. Желаемый резерв также допускает ноль.
4. Регулярные расходы: можно создать одну или несколько статей либо пропустить шаг.
5. Краткая сводка и «Начать планирование».

Изменения мастера сохранять после успешно завершённого шага. Незавершённый мастер продолжать с первого незавершённого шага после повторного открытия. До завершения не показывать данные как готовый достоверный план. Созданные статьи не дублировать при возврате на шаг.

Предложить названия и категории типичных расходов, но не создавать реальные платежи с демонстрационными суммами. Пустые значения суммы требуют ввода.

### 4.2. План

Видимое содержимое в порядке сверху вниз:

1. Название текущего месяца и быстрый переход к настройке темы.
2. Показатели: «Денег сейчас», «Ближайший доход», «На жизнь до следующего дохода», «Резерв», «Можно потратить сейчас».
3. Месячные суммы: доходы/расходы/разница для плана и факта; отдельно осталось получить и оплатить. Разница не подписывается как банковский остаток.
4. Предупреждения с суммой, датой и ссылками на затронутые записи.
5. Основные действия «Добавить расход» и «Добавить доход».
6. Группы рекомендаций: «Из текущего остатка», затем ожидаемые поступления по датам. Полученные зарплата и аванс отмечены как полученные; новый план не предполагает их повторного получения.
7. Отдельные сворачиваемые блоки «Не помещается в план» для необязательных расходов и «Оплачено» для текущего месяца. Просроченные обязательные расходы размещать перед обычными группами.
8. Прогноз до конца месяца и строка «Сохранить до следующей зарплаты» для границы месяца.

Карточка расхода: название, категория, сумма, крайний срок, рекомендованная или ручная дата, группа финансирования, обязательность, исходный месяц при переносе, объяснение рекомендации, галочка и меню действий. Для оплаченного расхода показывать фактическую сумму и дату, а не устаревшую плановую сумму.

Группа финансирования обозначает период поступления в рамках общего баланса. Если используются накопленные деньги, пояснение: «Из поступления и сохранённого остатка». Точную разбивку платежа по виртуальным источникам не показывать.

Фильтры: все/неоплаченные/оплаченные, обязательность, категория. Поиск по названию и заметке без учёта регистра. Фильтры изменяют видимый список, но не финансовые итоги. Предусмотреть «Сбросить фильтры».

Порядок карточек: просрочка, затем рекомендованная дата, крайний срок, обязательность, время создания, идентификатор. Сортировка стабильна после перезагрузки. Drag-and-drop не требуется.

### 4.3. Итоги

Переключение «Месяц / Год», выбор года и при необходимости месяца. Доступны периоды с историей и текущий год. Пользователь может добавить историческую операцию за прошлый период через этот экран.

Для месяца: фактические доходы, расходы, разница, распределение расходов по категориям, список операций с фильтрами по типу и категории. Для текущего месяца дополнительно показывать текущий план. Прошлые планы не восстанавливать и не сравнивать с первоначальными обещаниями.

Для года: фактические доходы, расходы, разница; 12 строк месяцев; диаграмма парных столбцов доходов и расходов; распределение расходов по категориям. Нажатие на месяц открывает его операции. Рядом с диаграммой всегда доступны точные текстовые значения. При нулевых расходах не делить на ноль и показывать «Расходов нет».

Будущие месяцы текущего года обозначать «Ещё не наступил». Прошедшие без внесённых операций — «Нет данных», кроме месяцев, которые пользователь явно отметил полностью внесёнными. Неполные периоды обозначать «Неполные данные». Год с такими месяцами — «Итоги по внесённым данным».

Есть действие «Все операции месяца внесены» с возможностью снять отметку. Оно меняет только признак полноты данных и не создаёт операции. Месяц начала использования считается неполным до явной отметки пользователя. Генерация планов не подтверждает полноту фактической истории.

### 4.4. Регулярные

Список шаблонов расходов с названием, категорией, обычной суммой, днём срока, обязательностью, правилом переноса и активностью. Действия: добавить, редактировать, включить/отключить, архивировать.

Редактирование шаблона действует на новые экземпляры будущих месяцев. Отдельный флажок «Применить к неоплаченному расходу текущего месяца» доступен, если такой экземпляр существует; по умолчанию выключен. Фактические операции не меняются. Включение новой статьи в текущем месяце создаёт один экземпляр, даже если срок уже прошёл: показать просрочку, не считать её оплатой.

Отключение или архивирование прекращает создание будущих экземпляров, но сохраняет существующие расходы и историю. Если нужно убрать существующий неоплаченный расход, пользователь отменяет именно его.

### 4.5. Настройки

Разделы: текущий остаток, регулярные доходы, деньги на жизнь и резерв, категории, оформление, резервная копия, сведения о локальном хранении, очистка данных.

Корректировка остатка — отдельная форма с датой «Сегодня», новой суммой и необязательной заметкой. Произвольная задняя дата корректировки не поддерживается: исторические операции добавляются отдельно. Перед сохранением пояснить, что введённая сумма уже включает все фактические операции, внесённые к этому моменту.

Регулярные доходы: сумма и день каждой зарплаты/аванса, включение/отключение. Изменение правила — для будущих экземпляров; изменение конкретной даты или суммы текущего поступления — в карточке этого дохода.

Есть выбор суммы на жизнь после зарплаты и аванса; для периодов без регулярных поступлений — сумма на календарный месяц. Для текущего периода пользователь может изменить оставшуюся сумму, не пересчитывая уже внесённые фактические покупки.

## 5. Формы и действия с записями

### 5.1. Разовый расход

| Поле | Правило |
| --- | --- |
| Название | Обязательное, 1–100 символов после удаления пробелов по краям. |
| Сумма | Обязательная положительная сумма, не более двух знаков после разделителя. |
| Категория | Обязательная; по умолчанию «Другое». |
| Срок оплаты | Обязательный для будущего/неоплаченного расхода, по умолчанию сегодня. |
| Обязательный | По умолчанию включён; пользователь может выключить. |
| Входит в бюджет на жизнь | По умолчанию включён для категорий «Продукты» и «Личные нужды», в остальных выключен; доступна ручная смена. |
| Уже оплачено | По умолчанию выключено. При включении появляются фактическая дата и сумма. |
| Ручная дата оплаты | Необязательна; без неё работает автоматическая рекомендация. |
| Заметка | Необязательная, до 500 символов. |

Запланированная трата, входящая в бюджет на жизнь, рассматривается как часть необходимых расходов на жизнь, а не как дополнительная трата поверх того же бюджета. При её добавлении автоматически включать обязательность с пояснением; пользователь может убрать признак бюджета на жизнь и затем изменить обязательность.

Внеплановый расход — тот же разовый расход с информационной меткой «Внеплановый»; отдельный механизм расчёта для него не нужен.

### 5.2. Шаблон расхода

Поля: название, сумма, категория, день месяца 1–31, обязательность, признак бюджета на жизнь, активность и правило для неоплаченного экземпляра.

Для обязательной статьи правило всегда «Сохранять задолженность» и не редактируется. Для необязательной доступны:

- «Переносить»: перенести старый неоплаченный экземпляр отдельно от нового регулярного платежа. По умолчанию выбран этот вариант.
- «Пропускать»: при смене месяца отменить старый неоплаченный экземпляр и создать только новую оплату месяца. В истории отмены указать «Пропущен по правилу статьи».

Для необязательного разового расхода правило всегда «Переносить», если пользователь не отменил его вручную. Срок 31-го в коротком месяце становится последним существующим днём.

### 5.3. Доход

Разовый доход: название, положительная сумма, ожидаемая дата, заметка, переключатель «Уже получен». При получении — фактическая дата по умолчанию сегодня и сумма по умолчанию равна ожидаемой. Категории доходов для первой версии фиксированы: «Зарплата», «Аванс», «Дополнительный доход».

Дополнительные доходы вносятся только вручную и не повторяются автоматически. Не использовать их как новые границы бюджета на жизнь: они пополняют действующий период.

### 5.4. Быстрые отметки и исправления

Нажатие галочки неоплаченного расхода создаёт полную оплату на плановую сумму с датой сегодня. Доход отмечается кнопкой «Получен» аналогично. Сохранить атомарно и показать короткое сообщение с «Отменить» на 8 секунд. Повторный тап во время сохранения игнорировать.

Действие «Исправить оплату/поступление» открывает сумму и дату. Новая фактическая сумма может отличаться от ожидаемой: исходный план сохраняется как справочное поле, экземпляр считается полностью закрытым фактической суммой. Доплаты к этому же экземпляру нет; если пользователь реально платит другую отдельную сумму, нужна отдельная запись.

Фактическая дата не позже сегодня. Исправленная сумма означает полную конечную стоимость расхода, а не частично внесённый платёж: это пояснить в форме. Снятие галочки отменяет соответствующую активную операцию и возвращает экземпляр в ожидаемое состояние. Повторная оплата создаёт новую операцию, сохраняя отменённую для технической истории.

Отмена неоплаченного расхода/ожидаемого дохода требует короткого подтверждения и сохраняет запись со статусом «Отменён». Физически не удалять экземпляр, чтобы генерация не создала его снова. Для оплаченного/полученного экземпляра сначала предложить отменить фактическую отметку; одной кнопкой незаметно уничтожать факт нельзя.

### 5.5. Исторические операции

Можно создать фактический доход/расход за прошлую дату и исправить существующую запись. Историческая запись не запускает генерацию регулярных шаблонов за тот месяц.

Если дата раньше даты точки остатка, запись автоматически считается уже учтённой в остатке и влияет только на аналитику. При совпадении дат доступен флажок «Уже учтено в введённом остатке»; по умолчанию выключен для новой записи. Для дат после точки остатка флажок недоступен: такая операция участвует в изменении баланса.

Для фактической траты на жизнь с датой, совпадающей с датой текущей точки бюджета, дополнительно доступен независимый флажок «Уже учтено в оставшемся бюджете на жизнь». По умолчанию выключен. При включении добавить идентификатор операции в `includedLivingOperationIds`. Это позволяет позднее внести сегодняшнюю покупку, уже учтённую пользователем при настройке оставшейся суммы. Флажок остатка денег не включает флажок бюджета автоматически: это две независимые точки.

Исправление/отмена записи, уже включённой в точку остатка, не меняет вручную подтверждённый остаток. Перед подтверждением показывать: «Изменится история. Если сумма денег сейчас другая, уточните остаток». Для не включённой записи баланс изменяется на разницу между старой и новой операцией.

### 5.6. Категории

Предустановленные категории: «Ипотека», «Кредиты», «Коммунальные услуги», «Школа и питание», «Кружки и секции», «Связь», «Продукты», «Личные нужды», «Транспорт», «Здоровье», «Другое».

Можно добавить, переименовать, архивировать и восстановить категорию. Название 1–40 символов; совпадения без учёта регистра запрещены среди всех категорий. Если такое имя уже архивировано, предложить восстановить его вместо нового идентификатора. «Другое» нельзя архивировать. Архивная категория остаётся в истории и отчётах, но не предлагается для новых записей. Категории физически не удаляются, объединение категорий не требуется. Существующий шаблон с архивной категорией сохраняет её; при создании новой статьи доступны только активные категории.

Переименование изменяет подпись категории во всех отчётах, но не суммы и не принадлежность операций. Изменение категории конкретной оплаченной записи обновляет её группу в аналитике. Признак «Входит в бюджет на жизнь» хранится отдельно: одно переименование категории не меняет расчёт бюджета.

## 6. Правила дат и смены месяца

Дата — строка `YYYY-MM-DD`; месяц — `YYYY-MM`. Сегодня определяется календарной датой устройства. Нельзя получать её через обрезание UTC-строки `toISOString()`. Календарную арифметику выполнять по компонентам, исключая сдвиги из-за часового пояса и переходов времени.

Для регулярного дохода: взять день правила, ограничить последним днём месяца, перенести субботу на пятницу и воскресенье на пятницу. Ручная дата экземпляра имеет приоритет и не переносится повторно. Дата фактического получения имеет приоритет над ожидаемой для истории и границ уже полученного дохода.

Если ожидаемый доход имеет дату раньше сегодня и не отмечен полученным, показать «Поступление не подтверждено». В будущий расчёт он не зачисляется автоматически ни прошлой датой, ни сегодняшней. Пользователь должен подтвердить получение или перенести ожидаемую дату.

При загрузке, событии возвращения страницы в видимое состояние и изменении календарной даты во время работы запускать обслуживание месяца. Во время открытой формы ничего не закрывать; обновить состояние и пересчитать после сохранения/отмены формы. Проверка даты раз в минуту допустима, но не является фоновой задачей закрытого приложения.

Обслуживание месяца выполняется одной сохраняемой транзакцией:

1. Зафиксировать новую дату и определить текущий месяц.
2. Для уже существующих неоплаченных обязательных расходов сохранить срок и исходный месяц, показать задолженность.
3. Для уже существующих необязательных расходов с правилом «Переносить» изменить плановый месяц сразу на текущий, сохранить исходный месяц, день исходного срока и журнал переносов. Новый срок — тот же день текущего месяца с ограничением последним днём. Переносить один и тот же экземпляр, не копировать его.
4. Для неоплаченных необязательных экземпляров с правилом «Пропускать» установить отмену, если их плановый месяц закончился.
5. Создать отсутствующие регулярные доходы и расходы за текущий месяц, если соответствующие правила активны. Для дохода соседнего номинального месяца, дата которого из-за переноса попала в текущий календарный месяц, применить исключение 9.1. Уникальность — пара «идентификатор правила/шаблона + исходный месяц», в том числе среди отменённых экземпляров.
6. Не создавать новые экземпляры за месяцы, в которые приложение не открывали. Не придумывать факты за эти месяцы.
7. Сохранить изменения, затем пересчитать план и отчёты.

При переходе через год правило такое же. Повторный запуск не создаёт дополнительных экземпляров или повторного переноса в тот же месяц. Оплаченные записи и полученные доходы не переносятся. Отменённые не восстанавливаются генератором.

Если новый регулярный платёж и перенесённый старый относятся к одной статье, показывать оба с исходными месяцами. Для задолженности по обязательной статье также сохраняется новый экземпляр: фактически это могут быть две суммы.

## 7. Бюджет на жизнь и резерв

### 7.1. Периоды бюджета

Границы задаются регулярными зарплатой и авансом с учётом переноса и ручных дат. Если два регулярных поступления оказались в один день, объединить их в одну границу, а их стандартные бюджеты сложить. Дополнительный доход не создаёт отдельный бюджет и не обнуляет текущий.

Если активен один регулярный доход, период идёт от него до следующего такого дохода. Если нет ни одного — использовать календарный месяц. Для служебного прогноза допускается вычислить границы и суммы будущего периода из правил без сохранения будущих экземпляров.

Для текущего периода можно задать оставшуюся сумму на жизнь. Хранить её как отдельную настройку периода с датой начала покрытия сегодня; уже потраченные до этой даты суммы не уменьшать повторно. Для стандартного будущего периода покрытие начинается в день поступления.

Редактирование «Осталось на жизнь» создаёт новую точку бюджета на сегодня. Все уже записанные активные расходные операции отметить учтёнными в ней по идентификаторам, включая записи сегодняшнего дня: при расчёте из них используются только расходы на жизнь. Сохранение всех идентификаторов защищает и от повторного списания после исправления категории/признака старой покупки. Новые покупки уменьшают оставшийся бюджет, кроме явно отмеченных уже учтёнными по правилу 5.5.

### 7.2. Замещение планового бюджета фактами

Для каждого периода определить:

- `L` — настроенный бюджет периода/оставшейся части;
- `A` — сумма активных фактических расходов с признаком бюджета на жизнь, относящихся к покрываемой части и не включённых в новую точку бюджета;
- `Q` — сумма запланированных неоплаченных расходов на жизнь с датой в покрываемой части;
- `U = max(0, L - A - Q)` — ещё не расписанный бюджет на жизнь.

`A` уже уменьшило фактический денежный остаток. `Q` присутствует в плане как конкретные платежи. В прогнозе дополнительно резервируется только `U`, а не `L` второй раз.

Если `A + Q > L`, показать превышение бюджета. Оно не запрещает запись расхода. Отмена или исправление фактической покупки пересчитывает бюджет, кроме покупок, которые уже включены в новую точку оставшегося бюджета: их исправление требует при необходимости уточнить эту точку вручную.

Совокупная фактическая трата за день/неделю допустима одним расходом с выбранной фактической датой. Весь расход относится к этой дате; приложение не делит его между месяцами автоматически.

### 7.3. Мягкий резерв

Пользователь задаёт желаемую сумму `T >= 0`. Из расчёта после обязательных платежей и бюджета на жизнь определить минимальный защищённый прогнозный остаток `M` на всём расчётном горизонте, включая сегодня.

Реально защищаемый резерв: `R = min(T, max(0, M))`. Если `M < 0`, резерв равен нулю, а недостаток показывается отдельно. Если свободных средств мало, `R` меньше цели: надпись «Резерв 2 000 ₽ из желаемых 5 000 ₽», без ложного кассового разрыва только из-за недостигнутой цели.

Резерв определяется до включения необязательных расходов: последние не должны автоматически тратить его. Фактическую или вручную закреплённую трату, расходующую резерв, записывать можно; показывать предупреждение и пересчитывать его доступную величину.

Резерв не списывается из реального баланса и не входит в месячные расходы. Если все настройки бюджета и резерва нулевые, план честно рассчитывает только введённые обязательства; показывать ненавязчивое предложение настроить деньги на жизнь.

## 8. Расчёт фактического остатка

Точка остатка содержит сумму, дату и идентификаторы фактических операций, уже включённых в эту сумму. При первоначальном вводе перечень пуст. При корректировке на сегодня включить все существующие активные фактические операции с датой не позже сегодня.

`B = сумма точки остатка + сумма активных доходных операций вне перечня включённых - сумма активных расходных операций вне перечня включённых`.

Операции с датой раньше точки остатка всегда должны быть в перечне включённых. Фактические операции из будущего запрещены. История для аналитики использует все активные операции независимо от этого перечня.

При создании исторической операции до даты точки автоматически добавить её идентификатор в перечень. Для той же даты использовать флажок формы. При исправлении даты, перешедшей за границу точки остатка, пересчитать включение по этим правилам и показать предварительное новое значение баланса до подтверждения.

Отмена включённой операции не меняет сумму точки; отмена не включённой восстанавливает влияние её суммы. Повторная отметка создаёт новую операцию и заново применяет правила включения. Хранить отменённую операцию со статусом `void`, чтобы действие было прослеживаемым; в итоги и баланс она не входит.

Фактический остаток может быть отрицательным; не заменять его нулём. Отрицательный остаток показывать как отдельное предупреждение.

## 9. Детерминированный алгоритм планирования

### 9.1. Расчётный горизонт и исходные события

Начало расчёта — сегодня. Конец `H` — первая дата регулярного дохода строго после последнего дня текущего месяца; `H` не входит в горизонт. Если регулярных доходов нет, `H` — первый день следующего месяца. Для поиска границы можно вычислить ближайшие два будущих номинальных месяца из правил; это не генерация задолженностей за эти месяцы.

В расчёт входят:

- фактический остаток `B`;
- ожидаемые доходы с датой от сегодня включительно до `H` исключительно;
- существующие обязательные неоплаченные расходы текущего месяца и просроченные обязательства;
- существующие запланированные расходы на жизнь;
- ручные даты необязательных расходов как закреплённые пользователем решения;
- известные обязательные регулярные расходы следующего месяца со сроком раньше `H`, вычисленные из шаблонов, либо уже существующие экземпляры вместо них;
- бюджеты на жизнь всех пересекающихся периодов.

Факт уже включён в `B` и не повторяется среди будущих событий. Будущие служебные экземпляры используются в расчёте только один раз по ключу шаблона и месяца. У них нет галочки оплаты, пока они не стали настоящими экземплярами плана. Не включать неизвестные доходы или расходы.

Особый случай регулярного дохода с днём 1: перенос выходного может поместить доход следующего номинального месяца в текущий календарный месяц. Такой доход материализовать как экземпляр с исходным номинальным месяцем, чтобы пользователь мог отметить получение. Это исключение касается поступления, попадающего в текущий месяц, а не генерации расходов за пропущенные месяцы. Проверять соседние номинальные месяцы и уникальность ключа.

Ручная дата ожидаемого дохода может находиться за пределами текущего месяца; сохранять её, пояснять это в списке доходов и учитывать только при попадании в горизонт. Новые запланированные разовые расходы первой версии ограничены текущим месяцем: срок не позже его последнего дня; прошедший срок допустим с предупреждением. Запланировать новый следующий месяц отдельным экраном нельзя.

### 9.2. Дата оплаты и группа финансирования

Для автоматического плана рекомендованная дата — крайний срок включительно, либо сегодня, если расход уже просрочен. Такое правило сохраняет ликвидность до срока, а группа поступления объясняет, из каких денег подготовить оплату. Пользователь вправе оплатить раньше быстрой галочкой или установить ручную дату.

Ручная дата неоплаченного расхода допустима в пределах текущего месяца, не раньше сегодня. Дата после срока допускается только после подтверждения предупреждения «Оплата будет позже срока». После наступления закреплённой даты неоплаченный расход автоматически получает расчётную дату сегодня; исходная ручная дата сохраняется для пояснения.

Группа финансирования — последнее доступное ожидаемое поступление с датой не позже расчётной даты оплаты. Если такого будущего поступления нет, использовать текущий остаток. Доход в тот же день доступен первым. Просроченный неподтверждённый доход не является источником. При нескольких доходах одного дня объединить события для баланса, но сохранить названия составляющих в группе.

Установление ручной даты не означает ручного подтверждения наличия денег. Проверка дефицита выполняется и для неё. При недостатке средств обязательный расход остаётся в плане с датой и отметкой нехватки; не подписывать его как обеспеченный.

### 9.3. Две кривые остатка

Считать две последовательности значений по календарным датам:

1. Денежная: `B + ожидаемые поступления - конкретные запланированные платежи`.
2. Защищённая: денежная последовательность минус ещё не расписанный бюджет на жизнь `U`.

`U` резервировать виртуальным событием в первый день покрываемой части периода, но не раньше сегодня. Это консервативно защищает полную оставшуюся сумму до следующего дохода. Виртуальная строка подписана «Оставить на жизнь», не создаёт фактический расход и не входит в фактическую аналитику.

Порядок в один день:

1. Ожидаемые доходы.
2. Виртуальное резервирование бюджета на жизнь — только для защищённой последовательности.
3. Обязательные расходы и конкретные расходы на жизнь.
4. Закреплённые ручной датой необязательные расходы.
5. Принятые автоматические необязательные расходы.

В каждой группе платежей порядок: исходный крайний срок, затем время создания, затем идентификатор. Считать промежуточный остаток после каждой операции, а не только итог дня. Доходы одного дня можно предварительно сложить. Значение до первого события, равное `B`, также входит в поиск минимума.

Отрицательная денежная последовательность — кассовый разрыв по конкретным платежам. Неотрицательная денежная при отрицательной защищённой — нехватка установленного бюджета на жизнь. Показывать эти состояния разными текстами, не смешивать с недостигнутой целью резерва.

### 9.4. Очередность и включение необязательных расходов

1. Построить обязательный план, включающий расходы на жизнь и служебные ранние обязательства следующего месяца.
2. Посчитать минимальный защищённый остаток `M0` и исходный доступный резерв `R0 = min(T, max(0, M0))`.
3. Добавить закреплённые ручной датой необязательные расходы. Посчитать `M1` и итоговую границу резерва `R = min(T, max(0, M1))`. Если `R < R0`, показать «Ручной план использует часть резерва». Ручные решения не отменять автоматически; при отрицательных значениях показать дефицит.
4. Остальные необязательные расходы отсортировать по крайнему сроку, времени создания, идентификатору. Для каждого временно добавить его в расчёт на рекомендованную дату.
5. Принять расход, только если денежная последовательность остаётся неотрицательной, а минимальная защищённая не ниже `R`. После принятия он остаётся в расчёте для проверки следующего кандидата.
6. Иначе убрать кандидата из исполнимого прогноза и показать в «Не помещается в план» с суммой и объяснением. Экземпляр не отменять: он остаётся неоплаченным и участвует в месячной сумме желаемых расходов. Его дальнейший перенос определяется правилом статьи.
7. Если обязательный/ручной план уже отрицателен, автоматически не добавлять необязательные расходы. Не пытаться скрыть дефицит изменением сроков.
8. Из окончательной защищённой последовательности получить `Mfinal`. «Можно потратить сейчас» = `max(0, Mfinal - R)`. Это безопасный дополнительный расход сегодня сверх уже принятого плана и бюджета; он не равен месячной разнице доходов/расходов.

Нельзя использовать только сумму месяца, сортировку по размеру платежа, случайный порядок или обещание будущего кредита. Деление платежа на части алгоритмом запрещено.

Предлагаемые действия при дефиците: проверить суммы, дату дохода, убрать/отложить необязательный расход, вручную уменьшить оставшийся бюджет на жизнь или добавить известный дополнительный доход. Эти действия выполняет пользователь; приложение не применяет их без его выбора.

### 9.5. Граница месяца и прогноз

На графике по умолчанию показывать даты текущего месяца и различать денежный и защищённый прогноз; служебную часть до `H` сделать раскрываемой. В текстовой таблице событий доступны все суммы и даты.

Строка «Сохранить до следующей зарплаты» перечисляет известные обязательства после конца месяца до `H` и остаток бюджета на жизнь периода, пересекающего границу. Пояснить, что это уже учтено в расчёте свободной суммы. Резерв показан отдельно, не прибавляется скрыто второй раз. Не выдавать полный бюджет пересекающегося периода за новый бюджет следующего месяца.

Доход в `H` и расходы со сроком в `H` не нужно обеспечивать деньгами предыдущего периода, поскольку доход того дня доступен первым. Если пользователь закрепил более раннюю оплату такого существующего расхода, учитывать её раннюю дату.

### 9.6. Статусы карточек

Базовый статус хранится, расчётные признаки вычисляются:

| Подпись | Условие |
| --- | --- |
| Оплачен | Есть одна активная расходная операция экземпляра. |
| Отменён | Пользователь отменил запись или применено правило пропуска. |
| Просрочен | Неоплачен, крайний срок раньше сегодня. |
| Пора оплатить | Неоплачен, срок сегодня или в ближайшие 3 календарных дня. |
| Запланирован | Остальной неоплаченный расход, включённый в план. |
| Не хватает денег | Обязательство или ручное решение в проблемном участке денежной последовательности. |
| Не помещается в план | Автоматический необязательный кандидат отклонён. |
| Перенесён | Дополнительная метка при непустом журнале переноса, а не замена статуса оплаты. |
| Бюджет превышен | Дополнительная метка для превышения денег на жизнь. |

Одновременно допустимы «Просрочен» и «Не хватает денег», а также «Перенесён» и «Оплачен». Не прятать один смысл другим. Для доходов: «Ожидается», «Получен», «Не подтверждено», «Отменён».

## 10. Правила месячных и годовых итогов

### 10.1. Факт

Для выбранного месяца `m`:

- `incomeFact(m)` — сумма активных доходных операций с фактической датой в `m`;
- `expenseFact(m)` — сумма активных расходных операций с фактической датой в `m`;
- `differenceFact(m) = incomeFact(m) - expenseFact(m)`.

Для года — сумма соответствующих фактических месяцев январь–декабрь. Отменённые операции не входят. Включение операции в точку остатка не исключает её из аналитики. Категории расходов считаются по активным расходным операциям; процент категории = её сумма / общие фактические расходы выбранного периода, с защитой от деления на ноль.

### 10.2. Текущий план

Для текущего месяца:

- доходы плана = фактические доходы месяца + ещё ожидаемые неотменённые доходы с ожидаемой датой в месяце;
- расходы плана = фактические расходы месяца + неоплаченные неотменённые расходы, расчётная дата которых приходится на месяц, включая обязательные долги и необязательные отклонённые кандидаты;
- разница плана = доходы плана - расходы плана;
- осталось получить/оплатить — только соответствующие ожидаемые/неоплаченные суммы.

Просроченный неподтверждённый доход с ожидаемой датой в этом месяце остаётся в плановой сумме с явной пометкой «Не подтверждено», но не финансирует будущие платежи. Поэтому плановый месячный итог может быть положительным при предупреждении о недостатке денег; объяснить это рядом с показателем.

У закрытого экземпляра ожидаемая сумма не добавляется: его фактическая сумма уже учтена в месяце фактической даты. Если оплатили октябрьский расход в ноябре, факт относится к ноябрю; октябрьские исторические итоги не увеличиваются.

Не расписанный бюджет на жизнь `U` показывать отдельно: «Дополнительно оставить на жизнь», поскольку это прогноз потребности, а не внесённый расход. Резерв отдельно. Служебные расходы следующего месяца не прибавляются к месячным расходам текущего.

Первоначальный месячный план не сохраняется отдельным снимком. При изменении записей пересчитываются текущий план и вся затронутая фактическая история.

### 11.2. Общие типы и идентификаторы

- `Money`: целое число копеек в пределах 0–99 999 999 999. Для сумм реальных/плановых операций строго больше нуля. Для остатка допустим тот же диапазон с отрицательным знаком. Проверять безопасные целые числа и итоговые суммы.
- `Date`: реальная календарная дата 1900–2100 в формате `YYYY-MM-DD`; пустая или несуществующая дата запрещена.
- `Month`: `YYYY-MM` в том же диапазоне.
- Новые пользовательские сущности — уникальные строки идентификаторов. Использовать `crypto.randomUUID()` при наличии, иначе генератор с проверкой коллизий в текущем состоянии.
- Регулярные экземпляры: стабильные ключи `income/<ruleId>/<YYYY-MM>` и `expense/<templateId>/<YYYY-MM>`. Номинальный исходный месяц не меняется при переносе.
- Время создания и технические timestamp не используются как даты оплаты.

`periodKey` — отсортированные идентификаторы регулярных доходов начальной границы, соединённые `+`; при отсутствии регулярных доходов — `calendar/YYYY-MM`. Граница из служебного будущего правила использует тот же стабильный идентификатор, который получит настоящий экземпляр.

При настройке текущего бюджета использовать одну активную точку на `periodKey`, старую заменять. Для уже объединённых поступлений один общий период. Если ручная корректировка доходов объединила ранее раздельные границы, суммировать их отдельные точки бюджета, а для частей без точки — стандартные суммы. Перечни включённых операций объединить без дубликатов; начало покрытия — самая ранняя дата покрытия составляющих, ограниченная началом нового периода. Если точек нет, использовать стандартные суммы. При последующем разделении общей границы сбросить общий override с видимым сообщением и применить стандартные суммы: пользователь может уточнить текущий оставшийся бюджет. Не терять фактические операции.

Начало покрытия override не раньше начала периода, а его включённые операции не участвуют повторно в `A`. При отсутствии override `coverageStartDate = начало периода`, включённых операций нет. Для уже прошедшей границы, когда пользователь впервые запускает приложение, мастер обязательно создаёт override с сегодняшней датой.

У обязательной статьи/экземпляра `rolloverPolicy = debt`; у необязательной — `carry` или `skip`; разовый необязательный — `carry`. При `isLiving = true` неоплаченный экземпляр считается необходимым, его `mandatory = true`. Эти комбинации валидировать.

### 11.4. Связи и атомарность

Операция копирует название, сумму и категорию на момент факта. Исправление конкретной оплаченной записи обновляет её активную операцию. Изменение шаблона этого не делает. Категории в отчётах объединяются по `categoryId` и используют текущее название категории.

У `paid/received` должен быть `operationId`, у `pending/expected/canceled` — `null`. Каждая активная операция связана с одним существующим источником нужного типа. У источника не может быть двух активных операций. `void`-операции могут сохранять связь с источником без обратного `operationId`.

Создание, отметка, исправление, отмена, перенос и импорт выполняются как целое изменение состояния: создать рабочую копию, проверить её, сериализовать и записать одним `setItem`, затем заменить состояние в памяти и обновить интерфейс. Если сохранение не удалось, старое состояние считается сохранённым, новое не выдаётся за сохранённое.

Дополнительный ключ `personalExpensePlanner.backup.v1` допустим для предыдущего валидного состояния. Перед заменой основного сохранить его старую версию. Если дополнительная копия не помещается, всё равно можно сохранить основной объект и сообщить, что внутренняя предыдущая копия не обновлена. Эта копия не заменяет экспорт JSON.

### 11.5. Загрузка и конфликты

При старте проверить чтение, временную запись и удаление тестового ключа localStorage. Затем прочитать основной объект, выполнить валидацию и обслуживание даты.

Пустое хранилище — мастер. Повреждённый объект — экран восстановления без автоматической перезаписи: предложить экспорт исходного текста, восстановление валидной внутренней копии, импорт или явный сброс. Неподдерживаемая будущая версия схемы — отказ от изменения с сохранением исходных данных.

Перед каждой записью сравнивать текущую `revision` хранилища с загруженной. При расхождении не затирать изменения другой вкладки: сообщение «Данные изменились в другой вкладке», выбор обновить экран либо экспортировать свой несохранённый вариант. Событие `storage` обновляет интерфейс сразу, если нет открытой изменённой формы; иначе показывает это же сообщение.

## 12. Проверки ввода и обработка ошибок

### 12.1. Суммы, даты и формы

- Принимать десятичную запятую или точку, обычные/неразрывные пробелы как разделители тысяч: `1 234,50` = 123450 копеек. После нормализации проверять всю строку, не использовать частичный `parseFloat`.
- Не принимать экспоненциальную запись, `NaN`, `Infinity`, посторонние символы, более двух дробных знаков, отрицательные доходы/расходы и значения вне диапазона. `0` допустим для баланса, бюджета и резерва, но не для действующего платежа.
- День правила — целое 1–31. Проверять реальные даты, в том числе високосные годы. Фактическая дата не позже сегодня.
- Название не может состоять только из пробелов. Поля описаны в разделе 5; сообщение об ошибке выводить рядом с полем.
- Не сбрасывать остальные поля после ошибки и не закрывать форму. Первое ошибочное поле получает фокус.
- Отмена формы не сохраняет частично введённую запись. При закрытии изменённой формы спросить «Не сохранять изменения?»; тема может меняться без потери формы.
- Основная кнопка недоступна во время сохранения. Кнопка «Отменить» краткого уведомления применяет обратное действие только к созданной операции, а не откатывает весь объект состояния. После следующей финансовой мутации устаревшее быстрое действие отмены скрыть.

### 12.2. Валидация состояния и импорта

Проверять идентификаторы и их уникальность, допустимые enum, типы полей, границы сумм, реальные даты, существование ссылок, уникальность регулярных ключей, связность статуса и операции, отсутствие двух активных фактов у одного источника, правила включения в точку остатка и корректность бюджетов.

Вложенные строки никогда не исполняются как код или HTML. Ввод и импортированные названия выводить через текстовые DOM-узлы. Не использовать `eval`, динамическую компиляцию или вставку непроверенных строк в `innerHTML`.

Максимальный файл импорта — 5 MiB; не более 20 000 элементов в каждом массиве и не более 200 активных шаблонов расходов. Проверять `Number.isSafeInteger` на промежуточных и итоговых суммах. При превышении — понятная ошибка, а не округлённый итог.

Конструировать нормализованный объект только из разрешённых полей. Не переносить неизвестные ключи в прототипы или настройки. Будущую версию схемы отвергать без попытки подогнать её к текущей. Отсутствие обязательного поля — ошибка; исключение — явно nullable поля и незавершённый мастер.

### 12.3. Сообщения

| Ситуация | Требуемое поведение |
| --- | --- |
| localStorage недоступен | Блокировать редактирование и объяснить, что браузер не позволяет сохранить данные. Не выдавать временную память за сохранение. |
| Не хватает места/ошибка записи | Оставить старое сохранённое состояние и открытую форму, сообщить «Изменения не сохранены»; предложить экспорт рабочей копии и повторить запись. |
| Повреждённые данные | Не очищать автоматически; экран восстановления по разделу 11.5. |
| Нет доходов | Рассчитывать от остатка, бюджет — на месяц, предложить настройку доходов. |
| Нет расходов | Пустое состояние с действием добавления, без демонстрационной задолженности. |

| Цель резерва не достигнута | Доступный резерв и цель, без ложной просрочки. |
| Неполная история | Итоги только по внесённым данным, возможность дополнить или подтвердить полноту. |

## 13. Экспорт, импорт и очистка

### 13.1. Экспорт JSON

Кнопка «Скачать резервную копию». Один файл `planner-backup-YYYY-MM-DD-HHmm.json` в UTF-8 с внешними полями `appId`, `schemaVersion`, `exportedAt`, `state`. Поле `state` содержит полный основной объект: историю, шаблоны, отменённые операции, точки остатка и бюджета, настройки и тему.

Не экспортировать вычисленные графики и итоги вместо первичных данных. Файл создаётся локально через Blob и ссылку скачивания, сетевых запросов нет. Если браузер не позволяет скачать, показать резервный JSON в отдельном поле с «Скопировать»; при недоступности Clipboard API текст можно выделить и скопировать вручную. Эти резервные действия не требуют нового файла приложения.

Показывать «Файл сформирован», а не обещать, что пользователь сохранил его в конкретную папку. Простой текст в настройках: «Сохраняйте копию перед переносом файлов или очисткой браузера».

### 13.2. Импорт JSON

1. Выбрать локальный `.json` через файловый input; запасной вариант — вставить JSON в поле.
2. Прочитать файл локально и полностью проверить. Не сохранять ничего на этапе проверки.
3. Показать дату копии, диапазон истории, количества доходов/расходов/активных фактов, тему и предупреждение о замене текущих данных.
4. Действия: «Скачать текущую копию», «Заменить данные», «Отмена». Замена требует явного подтверждения; автоматическое объединение копий не реализуется.
5. В рабочей копии выполнить обслуживание текущей даты, повторно проверить объект и поставить ревизию `max(текущая ревизия, ревизия копии) + 1`. Сохранить подготовленный объект одной транзакцией, затем применить тему и пересчитать показатели. Обслуживание даты не должно сначала заменить данные, а потом выполнять вторую потенциально неуспешную запись.
6. При любой ошибке старое состояние не меняется.

Если импортируется копия из будущей календарной даты с фактическими операциями позже сегодня устройства, отказать и предложить проверить дату телефона. Не обрезать такую историю молча.

### 13.3. Полная очистка

Действие находится только в настройках. Сначала предложить экспорт, затем потребовать ввести слово `УДАЛИТЬ`. Удалить только ключи данного продукта и вернуть мастер; не использовать `localStorage.clear()` для чужих ключей. Отмена не меняет данные. Операции с `void` не очищать отдельной автоматической функцией.

## 15. Локальный запуск на Android

Пользователь хранит три файла в одной доступной папке телефона и открывает `index.html` локально в браузере, который выполняет связанные локальные CSS/JS и предоставляет устойчивый localStorage. Путь к папке и выбранный браузер не менять без предварительного экспорта.

Поведение localStorage для документов `file://` не имеет одинаковой гарантии во всех браузерах. Это ограничение платформы, а не задача, решаемая заменой формулы или названием ключа. [MDN: localStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

Требования к реализации и проверке:

1. В HTML до загрузки JS есть статическое сообщение «Если приложение не запустилось, проверьте, что рядом находятся style.css и script.js и браузер разрешает открывать локальные файлы». При успешном старте скрыть его. `noscript` объясняет необходимость JavaScript.
2. До ввода финансовых данных выполняется проверка чтения/записи хранилища. При недоступности — блокировка сохранения, без скрытой работы только в памяти.
3. Тест на фактическом Android: открыть из выбранной папки, создать запись, закрыть вкладку и браузер, повторно открыть тот же файл тем же способом, проверить восстановление записи и темы.
4. Проверить загрузку внешних CSS и JS, ввод с экранной клавиатурой, импорт/экспорт, возврат из выбора файла и работу без сети.
5. Версию Android, браузер и способ открытия зафиксировать в результате проверки. Проверка на компьютере или при мобильной ширине не подтверждает доступ к локальным файлам на Android.
6. Если устройство/браузер не даёт нужные возможности, честно указать несовместимость. Не заменять проект сервером, APK, единственным HTML-файлом или облачным размещением без отдельного решения пользователя.

Изменение пути может открыть другую область хранения; перенос между устройствами выполняется JSON-копией. Очистка браузера и приватный режим не являются способом надёжного хранения. Универсальную работу во всех Android-браузерах не обещать.

### 17.3. Проверки интерфейса и производительности

Проверить пустой первый запуск, заполненный план, просрочку, два типа дефицита, оплаченные карточки, неполную аналитику, формы и ошибки в обеих темах на контрольных ширинах. Не должно быть обрезанных сумм, перекрытия нижней навигацией или горизонтальной прокрутки.

Для расчётных функций допустим отдельный временный тестовый стенд, но поставка остаётся из трёх файлов. Проверять деньги, даты, переносы, точку остатка, бюджет и отчёты автоматическими тестами с числовыми ожиданиями; интерфейс и Android — вручную или браузерным инструментом. Не подменять реальные финансовые проверки тестами, которые только повторяют написанную функцию.

Контрольный объём: 5 000 исторических операций и 200 текущих/служебных расходов. На компьютере изменение фильтра и пересчёт должны завершаться без заметной блокировки; ориентир расчёта менее 300 мс, без полного пересоздания DOM для каждой цифры в форме. На Android фиксировать реальные результаты, не объявлять производительность проверенной без устройства.

## 18. Организация реализации и готовность

Внутри `script.js` отделить функции календаря/денег, валидацию, генерацию/перенос, расчёт финансов, аналитику, хранение и DOM-контроллеры. Расчётные функции принимать состояние и явную дату, возвращать результат без записи в localStorage и побочных изменений. Изменять состояние только через централизованную сохраняемую мутацию.

Рекомендуемый порядок: модель и проверки → календарь и точка остатка → план и бюджет → формы/отметки → переносы → аналитика → резервные копии → две темы → проверка локального Android-запуска. Это порядок разработки, а не возможность исключить поздние этапы.

Продукт готов, когда реализованы все сценарии UC-01–UC-38, пройдены применимые AT-01–AT-36, нет ошибок в консоли при обычных действиях, данные переживают повторное открытие, а итоговая поставка содержит три согласованных файла.

Если Android недоступен для проверки, приложение можно передать как реализованное и проверенное на компьютере, но нельзя заявить подтверждённый локальный запуск на телефоне. В результате разработки отдельно перечислить выполненные проверки и оставшуюся проверку устройства. Невозможность выбранного браузера открыть локальные файлы — известное ограничение платформы, без самовольного расширения поставки.

Ни один пункт этого ТЗ не требует базы данных, серверной части, аккаунта, платной подписки, банковского доступа или отправки сообщений другим людям.
