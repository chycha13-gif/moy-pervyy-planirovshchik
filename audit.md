## Расхождения и предложения

### R1. Неверная полнота пустого месяца начала использования

- **ТЗ:** раздел 4.3 — месяц начала использования считается неполным до явного подтверждения пользователя.
- **Факт:** мастер сохраняет `monthCoverage[currentMonth] = "partial"`, но `monthStatus()` учитывает только явное `complete`. Без активных операций возвращает `empty`.
- **Воспроизведение:** закончить настройку без фактических операций → «Итоги». Показано «Нет данных» вместо «Неполные данные». Отметить «Все операции месяца внесены», затем снять отметку: снова «Нет данных» при сохранённом `partial`.
- **Влияние:** суммы корректны, но происхождение и полнота истории обозначены неверно, в том числе в годовом представлении.
- **Доделать:** учитывать явный `partial` до определения пустого месяца по отсутствию фактов. Месяцы без истории и без явной отметки оставить пустыми.
- **Проверка после исправления:** пустой первый месяц, снятие полноты, обычный прошлый месяц без истории и будущий месяц. Суммы и операции не должны меняться.
- **Код:** `script.js:660`, обработчик полноты около строки 1475, завершение мастера около строки 1747.

### R2. Просроченные карточки не сортируются по назначенной дате оплаты

- **ТЗ:** раздел 4.2 — после выделения просрочки сортировать по рекомендованной дате, сроку, обязательности, времени создания и идентификатору.
- **Факт:** общий расчёт сортирует платежи по дате оплаты, но отдельный список «Просроченные оплаты» использует сортировку по старому крайнему сроку.
- **Воспроизведение:** сегодня 15 октября. Платёж А: срок 1 октября, ручная оплата 30 октября. Платёж Б: срок 2 октября, ручная оплата 16 октября. Расчёт ставит Б перед А, интерфейс просрочек показывает А перед Б.
- **Влияние:** порядок подсказок не совпадает с фактической очередностью платежей; расчёт сумм этим примером не нарушен.
- **Доделать:** применять к просроченным карточкам сравнение по эффективной дате оплаты, затем остальные критерии ТЗ. Убедиться, что текст пояснения группы также корректен при ручной дате.
- **Проверка после исправления:** указанный пример, одинаковые даты и сроки, автоматическая просрочка, стабильность после перезагрузки.
- **Код:** сортировка `pending` около `script.js:1359`, вывод просрочек около строки 1369.

### R3. Нельзя увидеть отменённые и автоматически пропущенные записи

- **ТЗ:** раздел 5.2 требует в истории отмены «Пропущен по правилу статьи»; разделы 5.4 и 9.6 предусматривают сохранённый статус «Отменён».
- **Факт:** экземпляры сохраняются с `status: "canceled"` и причинами `skip`/`user`, генератор их не восстанавливает. Однако «План» показывает только ожидаемые и оплаченные записи, «Итоги» — активные факты. Пользовательского просмотра отменённых записей и человекочитаемой причины пропуска нет.
- **Воспроизведение:** создать неоплаченную регулярную статью с правилом «Пропускать», перейти в следующий месяц. Старый экземпляр отменён в JSON, но его причину нельзя посмотреть в интерфейсе.
- **Влияние:** требование хранения выполнено, требование отображения истории и статуса — частично.
- **Доделать:** предоставить компактный просмотр отменённых/пропущенных экземпляров с названием, месяцем, статусом и причиной. Например, отдельный фильтр или свёрнутый список. Восстановление отменённых записей ТЗ не требует.
- **Проверка после исправления:** ручная отмена дохода/расхода и автоматический пропуск, читаемая причина, отсутствие в финансовых суммах, сохранение после перезагрузки, отсутствие повторной генерации.
- **Код:** генерация пропуска `script.js:441`, фильтрация и вывод карточек в `renderPlan()`/`renderReports()`.

### R4. Предупреждение об исправлении учтённой операции есть не во всех точках входа

- **ТЗ:** раздел 5.5 — перед подтверждением исправления/отмены операции, включённой в точку остатка, показать «Изменится история. Если сумма денег сейчас другая, уточните остаток».
- **Факт:** в форме исправления через «Итоги» предупреждение есть. Та же операция через оплаченные карточки «Плана» открывает другую форму без этого предупреждения. Есть флажок учёта и предварительная сумма остатка, но требуемого объяснения нет. Общая форма дохода использует тот же механизм.
- **Воспроизведение:** отметить расход оплаченным → уточнить текущий остаток → открыть изменение оплаченного расхода из «Плана» и из «Итогов». Во втором случае предупреждение отображается, в первом — отсутствует.
- **Влияние:** пользователь может ожидать изменения остатка после изменения исторической суммы. Правильность сохранения подтверждённого остатка регрессионными тестами проверена.
- **Доделать:** одинаковое предупреждение для учтённого факта во всех формах исправления расходов и доходов. Снятие галочки уже содержит соответствующее объяснение.
- **Проверка после исправления:** оба типа операции, вход из обоих экранов, учтённый и неучтённый факт, отсутствие повторного списания.
- **Код:** `inclusionFields()` около `script.js:1059`, формы около строк 1092/1118, существующий вариант в `historyForm()` около строки 1435.

### R5. Дополнительный риск: статус офлайн-готовности не проверяет текущую целостность кеша

- **Связь с ТЗ:** дополнение PWA требует полного набора файлов до объявления готовности. Первичная установка это выполняет; здесь обнаружен отдельный сценарий последующей потери ресурса.
- **Факт:** `pwa.js` считает приложение готовым по наличию активного service worker (`navigator.serviceWorker.ready`), без проверки наличия всех файлов.
- **Воспроизведение на изолированном стенде:** дождаться успешной установки → удалить только `style.css` из кеша приложения → очистить HTTP-кеш → закрыть страницу → открыть новую без сети. Запрос CSS завершается `net::ERR_FAILED`, вместо Segoe UI используется Times New Roman, но приложение показывает «Готово к работе без интернета».
- **Ограничение вывода:** потеря CSS была создана искусственно; обычное открытие без сети с полным кешем успешно. Это не доказательство самопроизвольного удаления файлов на телефоне пользователя и не финансовая ошибка.
- **Рекомендация:** проверять наличие полного набора ресурсов перед показом готовности и при обнаружении неполного кеша предлагать подготовить его заново с сетью. Простая проверка обновлений не должна выдавать наличие активного worker за проверку целостности. Финансовый localStorage при восстановлении не очищать.
- **Проверка после улучшения:** отсутствие каждого обязательного ресурса, честный статус, восстановление с сетью и новый офлайн-запуск с сохранёнными финансовыми данными.
- **Код:** `pwa.js:54`, обработка отсутствующего ресурса в `sw.js`.

## Незавершённая ручная приёмка

**AT-36:** пользователь сообщил «работает» после инструкции установки. Это подтверждает успешный первоначальный запуск, но не весь сценарий. На TECNO Camon 30 / Android 16 / Chrome ещё нужны подтверждения:

1. Запись и выбранная тема сохраняются после полного закрытия приложения и Chrome.
2. При отключённых Wi-Fi и мобильных данных приложение запускается со значка, оформление и кнопки работают.
3. JSON действительно сохраняется в файл и затем выбирается и восстанавливается системным файловым окном Android.
4. Экранная клавиатура не закрывает необходимые поля и действия, обе темы читаемы и удобны.

Зафиксировать версию Chrome и результаты. Настольная автоматизация это требование не закрывает.
